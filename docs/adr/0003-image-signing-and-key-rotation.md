# ADR-0003: Image signing — cosign key pair with offline backup key, plus a rotation and leak plan

- **Status:** Accepted (the backup key is generated by the owner in Phase 1)
- **Date:** 2026-11-21
- **Phase:** 0

## Context

Installed systems only accept images that pass `/etc/containers/policy.json` (ADR-0004).
Whatever we put there decides who can push updates to every device, and what happens if a key
is lost. If the only trusted key is lost, **no device can ever update again** without manual
intervention.

### Option A — keyless (Sigstore Fulcio and Rekor, GitHub OIDC identity)

CI signs with a short-lived certificate tied to the workflow identity, so there is no key to
lose or leak. Checked against `containers-policy.json(5)` (containers/container-libs, main,
2026-11-21):

- The `fulcio` block requires `oidcIssuer` **and `subjectEmail`**.
- A GitHub Actions certificate carries a **URI** identity
  (`https://github.com/<owner>/<repo>/.github/workflows/build.yml@refs/heads/main`), not an email.
- There is no `subjectURI` or regex option upstream yet. Proposals exist but are not merged.

**So bootc and podman on the host cannot verify a GitHub-keyless signature today.** Keyless
would only work in CI, not where it matters.

### Option B — cosign key pair

This is what Universal Blue does: a primary key that CI uses, plus a backup key, both listed in
`policy.json` under `keyPaths`. A signature from *either* key is accepted.

## Decision

Option B, with this key setup:

| Key | Where the private key lives | Purpose |
|---|---|---|
| `kiezel.pub` / primary | GitHub Actions secret `SIGNING_SECRET` (password-protected cosign key) | Signs every build |
| `kiezel-backup.pub` / backup | **Offline only**: generated by the owner on their own machine, stored on two USB sticks in different places, plus a paper copy of the password. Never on GitHub and never on this dev machine. | Signs only during a rotation |

Both public keys ship in the image (`/etc/pki/containers/`) and are committed to the repo.
Signatures are also logged in Rekor (cosign default), which makes them publicly auditable.

### Protecting the primary key in GitHub

- The key and its password are **environment secrets** of a protected GitHub environment named
  `release`, not repository secrets. Only jobs that declare `environment: release` can read them.
- The `release` environment has:
  - **required reviewers** (the owner), so every signing run waits for a manual approval;
  - a **deployment branch rule**: only `main`. A pull request, including one from a fork,
    can never reach the key.
- **Branch protection on `main`:**
  - changes go through pull requests;
  - required status checks (validate, build, boot test) must pass;
  - no force-push, no deletion;
  - the rules also apply to administrators.
- Workflows run with least privilege (`permissions:` per job). Third-party actions are pinned
  to commit SHAs.
- **Trade-off:** every signed release needs a human click. If the owner is unavailable,
  devices get no new image, though they keep running the last good one. For a project with one
  maintainer this is the right side of the trade-off: a compromised workflow or dependency
  cannot sign by itself.

The primary key is generated in RAM (`/dev/shm`) on the maintainer's machine, piped directly
into `gh secret set --env release`, and then shredded. It never touches persistent disk or
the repository.

### Rotation plan (routine, at least yearly, or when someone with access leaves)

1. Generate a new primary key and put it in the GitHub secret.
2. Build image N, signed with the **old** primary key. Its `policy.json` lists
   `[old-primary, new-primary, backup]`.
3. Wait until devices have updated (Phase 2 adds an update-age metric; at least 30 days).
4. Build image N+1, signed with the new key. Its `policy.json` lists `[new-primary, backup]`.

### Leak plan (primary key compromised)

A leaked key alone is not enough to attack devices. The attacker must also push to
`ghcr.io/elstvictor05-droid/kiezel`, which needs GitHub write access, because the policy is
scoped to our repository. Still, act immediately:

1. Revoke all GitHub tokens and check the repository and GHCR audit log.
2. Sign an emergency image with the **backup key**. Its `policy.json` drops the leaked key and
   adds a new primary. Devices accept it because the backup key is already trusted.
3. Publish a security advisory in the repo, with the time window and affected digests.
4. Generate a new offline backup key at the next opportunity, using the routine rotation.

### Loss plan

- **Primary lost:** sign with the backup key as above, then rotate normally.
- **Both lost:** devices can no longer update automatically. Recovery is a documented manual
  procedure for an admin: boot, run `ujust kiezel-retrust` (Phase 5), which fetches the new
  public key over HTTPS from the repository and asks for confirmation of the fingerprint. This
  is why the backup key exists, and why it is offline and duplicated.

## Consequences

- One secret in GitHub (the primary key plus its password). Nothing else secret in the repo,
  and `.gitignore` blocks `*.key`.
- The owner must generate and safely store the backup key. That is a manual step in Phase 1.
- Revisit when containers/image supports Fulcio URI identities: keyless signing for CI plus the
  offline backup key would then remove the long-lived CI secret.
